Single-Writer SQLite/Yjs Architecture

NOXR-eueslset — branch: single-write-hail-mary

This branch eliminated the dual-write path (markdown + SQLite) from fp-core. SQLite/Yjs is now the single source of truth. The desktop app reads from the database via main-process IPC, detects cross-process changes via PRAGMA data_version polling, and uses optimistic mutations for instant UI feedback. Y.Doc compaction keeps the update table bounded.

3 Write Paths
CLI Write Path
  1. 1User runs fp issue create or fp issue update
  2. 2Calls createIssue() / updateIssue() in writes.ts
  3. 3Load Y.Doc from SQLite, mutate in memory
  4. 4Compute delta: Y.encodeStateAsUpdate(doc, sv)
  5. 5saveUpdateStrict() — INSERT into yjs_updates
  6. 6upsertIndex() — UPDATE issues_index (best-effort)
  7. 7Recompute child counts if parent changed
Cross-process effect: CLI writes increment SQLite's PRAGMA data_version, which the desktop's DatabasePoller detects within ~350ms (300ms poll + 50ms settle).
Desktop Write Path
  1. 1Renderer sends edit intent via IPC RPC
  2. 2Main process handler calls optimisticMutation()
  3. 3Build optimistic IssueSummary, bump patchSeq
  4. 4Broadcast ISSUES_PATCH immediately — <1ms
  5. 5Persist to SQLite in background (same writes.ts path)
  6. 6Call skipNextUpdate(issueId) on DatabasePoller
  7. 7Enqueue PUSH_UPDATES to sync worker
Rollback guard: If persist fails and patchSeq hasn't advanced (no concurrent edits), the optimistic patch is rolled back to cached state.
4 Database Watching

How cross-process changes reach the UI

  CLI->>DB: saveUpdateStrict INSERT yjs_updates
  Note over DB: data_version increments

  loop Every 300ms
    POLL->>DB: PRAGMA data_version
    POLL->>POLL: Compare with last known version
  end

  POLL->>DB: Detected change! Wait 50ms settle
  POLL->>DB: SELECT id, issue_id FROM yjs_updates WHERE id > lastSeenId
  POLL->>POLL: Filter out own-process writes via recentOwnWrites map

  POLL->>MAIN: Emit issues-patched event with changedIds
  MAIN->>MAIN: Read full issues from SQLite
  MAIN->>MAIN: Build IssueSummary array, bump patchSeq
  MAIN->>REND: Broadcast ISSUES_PATCH with seq + updates
  REND->>REND: useIssueSync merges into Zustand store
  REND->>REND: React re-renders with new data

Own-write suppression

When the main process writes to SQLite (via optimisticMutation), it calls skipNextUpdate(issueId) which adds the issue ID to a recentOwnWrites map with a 750ms TTL. The poller filters these out during processChanges() to prevent re-broadcasting changes the main process already broadcast optimistically.

Why PRAGMA data_version? — SQLite's sqlite3_update_hook only fires for same-connection writes. Since the CLI runs in a separate process with its own connection, PRAGMA data_version (which changes whenever any connection modifies the database) is the only reliable cross-process change detector. It's extremely cheap — no table scan, just reading a counter from the database header.

Sync Callbacks (fp-core)
The sync worker provides 4 callbacks to syncIssues(): loadLocalDoc loads Y.Doc from SQLite, saveLocalUpdate saves delta + reindexes, createLocalDoc creates new Y.Doc, persistSyncHash stores state vector hash for next handshake.
Avoiding Double Processing
When sync saves remote updates to SQLite, it sends SYNC_UPDATE to main. Main calls skipNextUpdate() before broadcasting, so the DatabasePoller won't re-process those same rows. Without this, every synced change would be broadcast twice.

Concurrency safety

Compaction captures MAX(id) before reading, so concurrent writes that arrive during compaction are preserved. The final DELETE only removes updates WHERE id <= maxUpdateId.

The snapshot stores last_update_id as a foreign key. loadIssue() reads the snapshot and then applies only updates WHERE id > last_update_id, so it always sees a consistent state.

An idempotency guard skips if another process already compacted past this point.

Sequence Gap Detection

The main process maintains a monotonically increasing patchSeq counter in AppState. Every ISSUES_PATCH event carries the current seq.

The renderer's useIssueSync hook compares each incoming seq against its last known value. If it detects a gap (missed patches), it schedules a full sync on next window focus to recover.

// useIssueSync.ts — gap detection const onSeqUpdate = (seq: number) => { const expected = lastSeq + 1; if (seq > expected) { // Missed patches — schedule full sync scheduleFullSync(); } setLastSeq(seq); };
